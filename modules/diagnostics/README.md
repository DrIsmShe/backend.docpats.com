# Модуль диагностической помощи

Помощь врачу в разборе клинического материала: анализы, заключения
исследований, клинический случай целиком. Монтируется в `/api/v1/diagnostics`.

## Чем это НЕ является

Модуль не ставит диагноз и не назначает лечение. Он указывает, на что обратить
внимание, что уточнить и чего в данных не хватает. Итог пишет и подписывает
врач — это зашито в код, а не только в тексты интерфейса:

- у каждого вывода поле `advisory: true` (`immutable`), и оно едет в API,
  выгрузку и любую интеграцию вместе с данными;
- дело нельзя закрыть без вывода врача (`closeCase` требует непустой текст);
- вывод модели никогда не подставляется в `doctorSummary` автоматически.

Причина не в осторожности формулировок. Система, которая говорит «диагноз: …»
про живого пациента, — медицинское изделие (MDR в ЕС, FDA в США). Пока модуль
остаётся вспомогательным, этот статус не наступает. Граница проходит именно
здесь, и её нельзя размывать «для удобства».

## Устройство

```
diagnostics/
  core/          дела, материалы, задания, выводы, обратная связь
  ai/            вызов модели, схема ответа, три анализатора
  <модальность>/ подмодуль на вид обследования (10 штук)
```

Подмодуль-модальность — плагин в реестре (`core/services/registry.js`), тот же
приём, что в `radiology/reading-systems`. Плагин описывает: что принимает, по
какому протоколу разбирает (чек-лист), какие красные флаги нельзя пропустить и
каким анализатором работает.

Анализаторов три, и их хватает на все десять модальностей:

| Анализатор | Кто использует | Что делает |
| --- | --- | --- |
| `report` | КТ, МРТ, УЗИ, рентген, ЭКГ, эндоскопия, гистология, кожа | разбирает текст заключения по протоколу модальности |
| `labs` | лаборатория | правила считают цифры, модель объясняет смысл |
| `clinical` | клинический случай | дифференциальный ряд, что дообследовать |

## Что уже умеет и чего не умеет

Все подмодули работают с **текстом**: описанием исследования, протоколом,
клиническими данными. Разбор самих изображений (пикселей) не подключён ни в
одном — и каждый подмодуль обязан объяснить это врачу полем `binaryNote`.
Это проверяется тестом `__tests__/diagnostics/modalities.test.js`: принять файл
и молча сделать вид, что «посмотрел», нельзя.

Подключение модели по изображению — отдельный шаг для одной модальности за раз,
вместе со стендом оценки. Начинать разумно с рентгена грудной клетки: там
больше всего готовых моделей и данных.

## Приватность

Это данные живых пациентов, в отличие от учебной арены (`modules/radiology`).
Поэтому:

- тексты (контекст, материалы, выводы, имена файлов) шифруются
  `common/utils/phiCrypto` — той же схемой, что `ClinicPatient`;
- имя пациента не хранится: есть ссылка на карту клиники либо метка врача;
- `.lean()` не вызывает геттеры, поэтому наружу отдаём только через
  `present*()` в `case.service.js` — иначе уйдёт шифртекст;
- разбор невозможен, пока врач не подтвердил **два разных** факта:
  `deidentified` (материалы обезличены) и `aiConsent` (согласие на обработку
  внешней моделью). Проверка живёт в сервисе, а не в контроллере: новый маршрут
  не сможет её обойти.

Учебный и клинический модули намеренно не смешаны: разные коллекции, разные
права, разный юридический статус.

## Происхождение выводов

У каждого задания пишется `provenance`: модель, версия промпта, отпечаток
входных данных, длительность, токены. Без этого на вопрос «почему система так
сказала» через полгода нельзя ответить ничем, кроме «ну, ИИ решил». Версию
промпта (`ai/runner.js` → `PROMPT_VERSION`) поднимать при каждом изменении
системного текста.

## Обратная связь врача

`verdict` у вывода (`agree` / `partly` / `disagree` + поправка) — это
одновременно метрика полезности и **разметка будущего датасета**. Ради неё
модуль стоит строить рано: данные копятся с первого дня работы. Свои модели
можно будет обучать только на них, и никак иначе.

## Журнал доступа (HIPAA)

Модуль пишет в канонический `hipaa_audit_logs` через `modules/diagnostics/audit.js`.
Два режима записи, и разница между ними не техническая:

- `trace()` — чтения и правки, fire-and-forget. Сбой журнала не должен ронять
  открытие дела.
- `traceEgress()` — **выход данных за пределы контура**: разбор, распознавание
  документа, выгрузка. Пишется синхронно и ДО действия: если журнал недоступен,
  данные наружу не уходят. Отказ в работе лучше неучтённой передачи PHI.

`metadata` содержит только структурные данные — сколько материалов, каких
видов, какой объём текста. **PHI туда не попадает никогда**: журнал живёт семь
лет и сам станет хранилищем персональных данных с первой же строкой текста
пациента.

## Пределы обращений к модели

`core/services/quota.service.js`. Считаются ЗАДАНИЯ (по одному на модальность),
а не нажатия: дело с восемью направлениями стоит восьми единиц. Окно
скользящее, счёт по записям в базе — счётчик в памяти обнулялся бы при каждом
деплое.

| Переменная | По умолчанию |
| --- | --- |
| `DIAGNOSTICS_ANALYZE_PER_HOUR` | 20 |
| `DIAGNOSTICS_ANALYZE_PER_DAY` | 60 |
| `DIAGNOSTICS_EXTRACT_PER_HOUR` | 40 |
| `DIAGNOSTICS_EXTRACT_PER_DAY` | 120 |

Отказ всегда говорит, через сколько можно повторить: «превышен лимит» без числа
— тупик.

## Выполнение разбора: воркер

`jobs/analysis.queue.js` (постановка) + `jobs/analysis.worker.js` (выполнение).

Раньше разбор шёл в процессе API, и перезапуск — деплой, `pm2 restart` —
обрывал его на середине: задание навсегда зависало в «выполняется», дело
навсегда в «идёт разбор». Это случилось в работе, не в теории.

```bash
npm run worker:diagnostics          # локально
pm2 start npm --name diagnostics-worker -- run worker:diagnostics   # прод
```

Воркер ОБЯЗАН импортировать `modules/diagnostics/index.js` — модальности
регистрируются при импорте, иначе каждое задание падает с «нет обработчика».

Запасной путь: если Redis недоступен, разбор выполняется в процессе API, как
раньше. Хуже, но лучше отказа врачу. Выключатель `DIAGNOSTICS_QUEUE=off`
возвращает прежнее поведение целиком.

Брошенные задания (старше 15 минут в `queued`/`running`) помечаются сбойными
при чтении дела и списка — `reapStaleJobs`. Это подстраховка на случай, когда
не сработало всё остальное.

## Обращение к модели: что настроено и почему

`ai/runner.js` — единственная дверь к модели. Настройки там не по умолчанию, и
у каждой есть причина:

| Настройка | Значение | Почему не по умолчанию |
| --- | --- | --- |
| `thinking` | `adaptive` | На Opus 5 мышление включено по умолчанию; задаём явно, чтобы это было видно в коде |
| `max_tokens` | 32 000 (разбор и распознавание) | Мышление делит бюджет с текстом ответа. Тесный потолок обрывает разбор на середине; запрос идёт стримом, так что HTTP-таймаут не ограничение |
| `output_config.effort` | `high` — разбор, `medium` — распознавание | API по умолчанию работает на `high`, и для распознавания это плата за размышления там, где нужна аккуратность. Проверено живым запросом на плотном бланке: на `medium` точность та же — 12 значений из 12 |
| `fallbacks` | `"default"` | Классификаторы иногда отклоняют клинический материал; режим `default` выбирает замену по категории отказа и не требует миграции при смене моделей |

Уровни усилий настраиваются: `DIAGNOSTICS_EFFORT_ANALYSIS`,
`DIAGNOSTICS_EFFORT_EXTRACTION`. Подобрать их можно только на своих данных.

Три исхода различаются по смыслу, и каждый даёт врачу свой совет:

- `refusal` — отказ фильтров. Категория пишется в лог (она отличает ложное
  срабатывание на описании отравления от осмысленного отказа), врачу
  предлагается переформулировать.
- `model_context_window_exceeded` — не поместился **вход**. Совет: разобрать
  материал частями. Раньше этот случай сваливался в «пустой ответ».
- `max_tokens` — оборвался **ответ**. Совет: сократить материал.

## Выгрузка

`GET /cases/:id/export` → HTML одним файлом (`core/services/export.service.js`).
Печатается в PDF из браузера; серверная генерация PDF потянула бы шрифты с
кириллицей и десятки мегабайт зависимостей ради того же результата.

Порядок разделов равен ответственности: **вывод врача идёт перед разбором ИИ**.
Тот, кто откроет файл через год, должен увидеть сначала решение врача.
Выводы, с которыми врач не согласился, из документа не вычищаются — это
подделка истории разбора.
